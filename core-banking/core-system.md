### 银行核心系统之综合前置（2020-04-24）

原文链接：[阅读原文](https://mp.weixin.qq.com/s?__biz=MzIzMTk2NjAzMg==&mid=2247484887&idx=1&sn=47d1d53f3b9a0647d182662fa3370141)

正文提炼要点：

- 综合前置是核心的"面"（外围连接器），与记账核心"里"相对；作为渠道与核心之间协议/格式转换的接口和缓冲，所有渠道都先与前置交互，分总行/分行前置并可相互调用实现异地服务。
- 平台完成数据包格式转换、路由选择、安全控制、交易控制、事务控制；由服务接入、中央核心系统、异步处理控制、服务接出四部分组成，接入柜面/ATM/POS/网银，接出银联、网银支付、银企直联、外汇买卖、基金、核心等；异步通道处理冲正、短信定制等低实时性服务。
- 中央核心按报文字段识别交易、选路由、调度服务、记/更新流水，支持同步、异步与按交易流程反向冲正；库表分平台配置类（渠道/服务/流水号/日切/机构配置）、平台参数类（业务日期/币种/通讯参数/错误码）、应用交易配置类（路由/流水/待冲正流水/响应码对照），中央核心主要操作流水表与待冲正流水表。
- 中央控制五步：取服务管理信息→记流水→动态调度服务流程→更新流水→判断冲正；异常时记流水/加载配置阶段丢弃请求，更新流水阶段按冲正标志写待冲正表。
- 路由 SEND（发后不等响应）与 CALL（等响应才继续，若不回送响应会超时触发冲正）；冲正事务管理轮询待冲正表（标志=1），策略 0 通知模式发起即视为成功、策略 1 请求模式需服务返回成功，超过最大冲正次数置 2 转人工手工冲正。
- 冲正典型场景：终端已置成功但主机账务包无响应（先扣款后缴费的转账/代缴费组合交易），终端重发请求取消流水，主机已成功则回滚，靠流水与冲正流水监控保障一致性。
- 复杂组合交易案例（卡 B 股股票转出）：柜台请求→总行前置识别路由→总分行机构调用接出到分行 CIF 查账户与卡等级→返回总行外汇卡中心划拨股票→更新流水并回报客户，全过程定长报文转 XML。

### 核心银行系统 之十八 灾备（2020-03-22）

原文链接：[阅读原文](https://mp.weixin.qq.com/s?__biz=MzIzMTk2NjAzMg==&mid=2247484831&idx=1&sn=4afc5d6f9b46d061d8203cbfd2b8c576)

正文提炼要点：

- IT 风险是巴塞尔操作风险中最专业、最难管理和计量的，核心系统升级与生产切换最敏感，完善切换方案与演练可降低操作风险资本要求、提高资本充足率；关键术语 BIA、RTO（停顿到必须恢复的时间）、RPO（必须恢复到的时间点）。
- 数据备份：在线备份（备份服务器+管理软件+客户端集中管理，策略含全/增量/差分/按需备份，恢复分全盘/个别文件/重定向）与远程磁带备份（投资少易实现但会丢数据、恢复时间长）。
- 数据复制分应用、数据库、系统、SAN 网络、存储五个层次，对应五种技术；存储级最成熟最常用，应用级开发投资最大、硬件投入最小、实施管理最难。
- 存储级同步复制（同城镜像 Metro Mirror）两地都写才返回 I/O 完成、零丢失但受距离限制（50-60 公里内响应接近，超 60 公里且 I/O 量大时延迟明显）；异步复制本地写成功即返回、秒级丢失风险、无距离限制，用一致性组（全局镜像 Global Mirror）保证写顺序；自适应模式分钟至小时级丢失。多中心有星型、一对二、多跳（同步同城+自适应异地）等方案。
- SAN 级复制解决异构存储问题且位于中间层不占主机 CPU，可做多时间点快照（如 256 个视图）防渐变式灾难；系统级基于卷管理软件、依赖系统且影响性能；数据库级靠日志传输（带宽要求低、RPO 受带宽与处理能力限制，如 Quest SharePlex）；应用级开发量大、可靠性差。
- 虚拟化容灾可整合存储消除孤岛、功能遗传、分级存储与统一管理，但读性能有二次读损失；两地三中心有级联、多目标、闭环三种，闭环（3DC Multi-Target Delta-Resync）切换后 B 中心可与 C 中心建立增量一致性异步复制，最为可靠。
- SHARE78 七级灾备（Tier0 无异地备份→Tier7 零丢失+自动恢复）；PPRC 同步（备份卷未更新则整笔写失败、强一致）与 XRC 异步（SDM 搬运、时间戳保顺序、秒级延迟、最多 14 个 XRC 耦合、DWDM/CNT 可数千公里）；GDPS=Parallel Sysplex+远程拷贝实现备份恢复自动化，GDPS/XRC 的 RTO 1-2 小时、RPO 不超过 2 分钟（SDM 靠状态/控制/日志三类数据集管理）。
- 案例：某行 DCC 三级架构（数据中心-前置-前端），灾备资源复用（平时作测试环境，灾难时切换）；某商业银行两地三中心——北京同城 1.5 公里以上同步（RTO<2h、RPO=0，2GB 裸光纤）、上海异地异步（RTO<4h、RPO<15min，1GB 专线），灾备主机与生产同型号同配置并保持同步变更。

### 银行核心系统之数据脱敏（2019-04-30）

原文链接：[阅读原文](https://mp.weixin.qq.com/s?__biz=MzIzMTk2NjAzMg==&mid=2247484257&idx=1&sn=b3cd47d85447629fc896420b5ef72555)

正文提炼要点：

- 数据脱敏（Data Masking/漂白/去隐私化/变形）按规则变形敏感信息，在开发测试等非生产与外包环境安全使用真实数据集；好处是增加可管理性、泄露可追溯、风险可控；背景是 2009《商业银行信息科技风险管理指引》与 2017《网络安全法》。
- 四类典型场景：权限控制（按角色查询征信/营销名单/反洗钱）、数据传播（给外包与合作机构）、流程管理（生产查询提取）、数据使用（研发测试；密码等业务连续性数据由测试/业务组提供白名单不脱敏）。
- 脱敏后须保四点特征：保持原有数据特征（身份证 17 位本体码+1 校验码，脱敏后仍须符合校验规则）、数据间一致性（出生年月与身份证内出生日期一致，ECIF/ODS/CRM 与核心一致）、业务规则关联性（主外键关联，证件号脱敏后同步刷新账号证件号对账表）、多次脱敏一致性。
- 现状调研：仅 44% 中小城商行有脱敏制度、25% 分类分级、12% 操作流程、8% 流程化自动化可监控审计；76% 靠手工脱敏、16% 手工造数、仅 8% 用专业工具。
- 实施六步：组织架构（决策/管理/执行/审计四类）、分类分级（机密/内部/公开，业务/系统运行支撑/网络配置管理数据）、数据申请使用策略、授权审批策略、高效脱敏策略、脱敏后装载使用（到期销毁）。
- 常见方法：替换（X/0/哈，易破解）、重排（易破解）、加密、截断（保模糊但不友好）、掩码（如 0****5，保长度与可辨识）、造数（随机生成符合校验规则的身份证；港澳证件须先按香港规则校验再按澳门）、日期偏移取整（降精度）；转换程序用数据字典搜表清单，新增表字段无需改程序，外围表与 ODS 历史数据也要脱敏。

### 银行核心系统之分布式微服务（2019-02-20）

原文链接：[阅读原文](https://mp.weixin.qq.com/s?__biz=MzIzMTk2NjAzMg==&mid=2247484186&idx=1&sn=7c22a28d68dd1eda38a4f4391cf5653c)

正文提炼要点：

- 微服务=单体拆为一组独立进程的小服务，轻量 RPC 通信、围绕业务能力构建、自动化独立部署（CI/CD）、可用不同语言和存储；优点是解耦业务复杂度、模块化边界强、可独立部署升级、技术多样；缺点是分布式复杂性、一致性（银行对资金要求更高）、运维与测试复杂。
- 架构六层：基础设施层、平台服务层、支撑服务层、业务服务层（聚合服务+基础服务）、网关层（黑名单过滤、安全认证）、接入层（负载均衡）。
- 一致性三级别：强一致（刚性事务 ACID，性能影响大，网银金融交易须与核心对账）、弱一致、最终一致（弱一致特例、借异步消息实现，业界大型分布式系统推崇）；微服务后本地事务变跨库远程调用，一致性无保障。
- 刚性事务：ACID、本地事务优缺点、X/Open DTP 两阶段提交（准备阶段可提交回滚并加锁，缺点是长时间资源占用、持久成本、故障点多、隔离恢复难题），标准分布式事务严格 ACID 但效率低、微服务下少用。
- CAP 定理（一致性/可用性/分区容错性）：CP 放弃可用性基本不选、AP 放弃强一致性常见于 NoSQL、CA 即单机数据库；BASE 理论（基本可用/柔性状态/最终一致）为可用性降低 C 与 I，原子性与持久性必须保障。
- 柔性事务四类：两阶段型（红包/更新客户账/收费）、补偿型、异步确保型（热点账户异步记账/核算分离/虚实账户余额更新）、最大努力通知型（动账短信/理财提前到期/商户通知/对账文件）；TCC 分 Try（业务检查+预留资源）、Confirm（真正执行且幂等）、Cancel（释放资源且幂等），位于业务服务层、开发成本高，适合强隔离严格一致且执行短的业务（账户、收费、转账）；可靠消息最终一致（支付宝/eBay）、最大努力通知（银行通知）。
- 作者理性观点：传统小行/民营行没必要上分布式微服务——创新成本巨大、拆出上千交易后跨网络传输效率未必提升、小行话语权少风险大；且应全行统一考虑，若核心分布式而外围传统则需 ESB 串接、配置与调用关系清理复杂；量小可加内存/CPU/机器解决，主张结合实际理性选择、谨慎规划。

### 银行核心系统之技术架构(一)（2019-01-20）

原文链接：[阅读原文](https://mp.weixin.qq.com/s?__biz=MzIzMTk2NjAzMg==&mid=2247484164&idx=1&sn=3ca38e06e7b2826e1f0ad37dbdf99f0a)

正文提炼要点：

- 三时代：主机时代、集群时代、分布式时代；主机凭强计算/I/O 与稳定安全支撑银行核心，代表特性 Parallel Sysplex（最多 32 个 LPAR 共享读写、并行计算与恢复、可不停机动态加入集群），促成集中式单体架构（单机+热备，故障自动切换；冷备需切外设通道并重启 OS 与应用才接管）。
- z/OS：IBM 大型机 OS（由 OS/390 发展），适合大负荷多并发大 I/O；地址空间（私有区域相互隔绝、有公共区域）、物理存储分实存与外存 AUX 靠页面调度移动、操作员经控制台管理；TSO 是命令输入处理器（类似 DOS），支撑 ISPF 菜单与 RMF。
- COBOL：语法接近英语、格式固定结构严谨，银行保险金融常用，一个程序修修补补用十几年；MOVE 赋值数值靠左、字符靠右。
- DB2：关系型数据库、OS/390 下数据库子系统，层次为表→表空间→数据库→存储组，支持分布式工作单元 DUOW（两阶段提交）；分区表空间每分区一个数据集与一个表、每表空间最多 254 分区、每分区 64GB、可单独或多区处理，REORG/COPY/RECOVER 可在表空间级；ROWID 唯一标识记录物理位置、每表一列、GENERATE ALWAYS/BY DEFAULT。
- CICS：IBM 事务处理平台中间件，提供联机事务处理与管理，构建表述/业务/数据逻辑三层；模块含系统管理模块、系统控制表、系统控制块；关键组件 TCP 终端管理、TCT 终端控制表、PCP 程序管理、PCT 程序控制表、KCP 任务管理、TCA 任务控制区、FCP 文件管理、FCT 文件控制表、SCP 存储管理（静态/动态分配）。
- 小结：主机集中式架构简化开发测试与灾备部署、开发人员只需关注业务，但成本高且封闭；随 Java 兴起与去 IOE，国内银行逐渐接受 Java 核心并采用集群化部署与服务化架构。

### 银行核心系统之交易渠道（2019-01-05）

原文链接：[阅读原文](https://mp.weixin.qq.com/s?__biz=MzIzMTk2NjAzMg==&mid=2247484153&idx=1&sn=df677b07f70d4ad2af9285be5221e185)

正文提炼要点：

- 交易分金融交易（账户入出账、余额变化并登记明细与传票，如存取款/转账/支付/缴费/代发）与非金融交易（查询或数据变更并登记修改前后明细）；渠道是核心支持交易的通道或提供访问界面的外围系统（综合前置/ECIF），每个渠道对应渠道号（如 TRM/200 柜面、EBK/008 网银、ATM/101）。
- 柜面分高柜（重时效与录入正确性、页面简单）与低柜（面对面、重界面交互与图形展示），渠道信息表用系统号细分（01 高柜/02 低柜）供大数据精准分析；网银分个人/单位/内部，大额交易用户首选网银（安全感、屏幕大）；微信支付宝为主流第三方支付；ATM 现金交易萎缩、成本高且防诈 24 小时到账。
- 渠道发展三阶段：单渠道（点）→多渠道（线）→全渠道（面，线上线下整合、各渠道交叉相连）；选渠道看便捷性（44% 因随时转账开通手机银行）、安全性（80% 关注）、提示性（动账前可疑账号检查、动账后短信）等。
- 前置系统只做请求预处理（格式/报文安全验证/加密）与通讯转出转入、无实际业务处理——"核心是心脏，前置是血管"；对接流程为业务梳理→技术对接（逐字段过必输/默认值/核心是否支持/逻辑转换赋值/影响范围，不确定字段打标）→测试上线（发报文模板填值、日志与断点定位；生产问题可脱敏报文回测试环境模拟）。
- 配置与运维：渠道信息表（渠道号/系统号/路由规则/交易码/平台日期/所属机构）、渠道限额表（日月年与单笔限额、笔数）、渠道日志表（请求响应报文与结果码）；渠道可参数化启停与调限额；健康监控对大量超时或动账短信失败告警；异常交易因链路长可能响应标志未变，须等总分核对隔日差异报表。
- 案例：SWIFT 管理平台对报文清分/打印/头寸配对/对账；网银购买他行代销理财资金流为理财平台查账户→冻结并短信→日终解冻扣款返回结果文件→备付金划产品过渡户→归集产品归集户。

### 核心银行系统之批量（完整版）（2019-10-23）

原文链接：[阅读原文](https://mp.weixin.qq.com/s?__biz=MzIzMTk2NjAzMg==&mid=2247484487&idx=1&sn=77c51fbef96993c3372b4184abbb1e64)

正文提炼要点：

- 批量处理子系统是核心"内核"，承接业务处理与会计报表的枢纽，稳定性与适应性是最基本要求；五大功能=统计分析（总分核对、试算平衡、日/月/年终统计）、交易补记账（日终补账、清算、平仓、内部户划转、年终决算，解决内部户科目热点、减轻联机负担）、批量业务处理（代收付、贷款到期还款、信用卡自动还款、定期转存、基金定投、结息）、对外供数、数据移行（投产移行/功能移行/系统维护）。
- 调度架构：START1-N 日间起始作业、STARTJOB 日终起始、关联作业标识前后等待关系、ENDJOB 日终结束（备份在其后）；数据集中后按业务分区拆开、跨分区交互，用 IBM TWS 统一调度并保证两分区同步日切，单分区宕机时正常分区等待故障分区恢复再日切。

### 银行核心系统之外汇买卖（2018-12-15）

### 小白科普：缓存（2019-02-01）

原文链接：[阅读原文](https://mp.weixin.qq.com/s?__biz=MzIzMTk2NjAzMg==&mid=2247484171&idx=1&sn=9b7cfd607778d8d58206e0401dfdb5f7)

正文提炼要点：

- 缓存是在目标数据节点暂存传输过来的数据，可配置存储位置/IP/目录、保留时间与自动清理；类型含 CPU 的 L1/L2 缓存、Linux 文件缓存、浏览器缓存。
- 作用原理：数据库连接昂贵（I/O、TCP 连接）且连接池有限，多用户大并发会等待、关系库读写需加锁；数据放内存，CPU 读取依次查一级/二级/三级缓存再到内存；速度类比 CPU 1 秒、内存 6 分钟、网络 19 年；缓存降低数据库访问频率、减轻压力、缩短响应时间。
- 缓存数据格式：语言专有（Java 序列化/反序列化）、语言独立（protobuf）、XML/JSON、字符串 key-value、基本数据结构（Map）。
- 缓存空间满：启动时设缓存大小，用 LRU（最近最少使用）算法清除。
- 机制：查询先查缓存，命中即返回、未命中查库并写缓存；插入可先写库再淘汰缓存或先淘汰再写库，并发下均可能不一致（A 查到旧值、B 写新值删缓存、A 把旧值写缓存）；核心系统按模块/交易/事务维度，交易维度流程为通过 Key 找 Map→写记录→写数据库；写缓存分直写 write-through 与回写 write-back（回写只改本级缓存、最后一次性写入内存以避免同地址反复写提效）；删除通过 Key 找 Map 删记录同时删库。

### SQL效率（2018-09-25）

原文链接：[阅读原文](https://mp.weixin.qq.com/s?__biz=MzIzMTk2NjAzMg==&mid=2247484020&idx=1&sn=eaa5f4af64f253913ab2fc6c7bce8aef)

正文提炼要点：

- 不良 SQL 源于不恰当索引设计、不充分连接条件、不可优化的 where 子句。
- 索引：主键/外键/常查询/范围查询/WHERE 及 order by、group by、distinct 字段应建索引（复合索引字段顺序须与关键字后字段顺序一致）；少用列、重复值多、text/image/bit 列不建索引，经常存取列避免索引；更新多的表索引一般不超 3 个最多 5 个；复合索引按查询频度排序、高频字段放前（首字段不出现在条件中则索引不被使用）。
- 执行原理：先查计划缓存复用执行计划→语法/语义/权限验证→优化选算法→按 FROM→WHERE→GROUP BY→聚合→HAVING→表达式→ORDER BY 顺序执行；where 条件从右向左执行，运算符优先级越高放最后、同运算符数据范围越大字段放最后。
- 优化：小表字段写左边、尽量不用 OR、强烈不用 NOT IN（多次扫描，改 NOT EXISTS 或外连接+判空；Exists 比 IN 快）、IN 列表高频值放前、能 union all 不用 union（少一次 distinct）、少返回多余行列、少子查询多用连接、Between 有时快于 IN、FROM 中数据量少的表作基础表、无必要不用 DISTINCT/ORDER BY、count(*) 稍快于 count(1) 但索引列计数最快、减少对表查询、使用表别名。

- 死锁是多线程因竞争资源互相等待、无外力则无法推进；业务分单用户与用户间业务，单用户很少死锁；DB2 报错 SQLCODE=-911、SQLSTATE=40001，原因码 00C90088 死锁、00C9008E 超时；可在 DB2MSTR 的 JESMSGLG 查锁表信息，OMEGAMON XE 看锁级别与交叉锁 SQL。
- 原因：系统资源竞争、进程推进顺序非法、信息量不对等（互相等对方消息）；四个必要条件（互斥、不剥夺、请求和保持、循环等待）须同时满足，循环等待只是必要非充分条件。
- 避免方法：加锁顺序（所有线程按相同顺序加锁，须事先知道所有锁并排序，实际需列出业务场景与跟踪日志确认锁序）；加锁时限（超时放弃并释放已占锁、随机退避重试，锁超时不一定是死锁）；银行家算法（资源分配前先做安全性检查——Need≤Available 试探分配后若仍存在安全序列则分配，否则等待；死锁是不安全状态，不安全状态未必死锁）。
- 银行家算法需预先知道各进程最大资源需求且进程数不固定，实际应用有限，但思想可借鉴。
- 案例（活期转账交叉锁）：两笔交易分别 DR DDAC/CR IBAC 与 DR IBAC/CR DDAC，IBAC 相同、DD 账户不同，因 DD 表设为页锁使相邻账号互相等待形成交叉锁；排查思路为查 DB2 log 确认表与时间→按账号查日志确认交易码→结合程序看 READ UPDATE 处→查表锁属性（SELECT LOCKRULE FROM SYSIBM.SYSTABLESPACE）→尝试页锁改行锁（ALTER TABLESPACE ... LOCKSIZE ROW）测试→最终优化程序 READ UPDATE 处理，不建议改表属性（严重影响效率）。
