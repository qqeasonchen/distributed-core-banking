# 核心银行业务模块、技术痛点与解决方案

> **本文定位**：按核心银行系统的业务模块逐一讲清"这个模块做什么、难在哪里、业界怎么解"，提炼有借鉴价值的知识点与选型判据。
> 每个模块都来自真实的新一代核心建设实践；**哪家银行何时投产、规模数字、完整案例**见 [cases.md](../cases.md)，
> **单元化与多活的架构方案**见 [architecture.md](architecture.md)，**迁移工程方法**见 [migration.md](migration.md)。

## 业务模块全景

新一代核心普遍按业务域拆成松耦合微服务。综合多家银行的公开架构，典型模块划分如下：

| 业务模块 | 核心职能 | 主要技术痛点 |
|---|---|---|
| **客户信息** | 客户主数据、统一客户视图、多法人客户管理 | 各系统客户数据割裂、无统一视图 |
| **账户体系** | 账户生命周期、多层级账户结构、I/II/III 类账户 | 账户离散、跨账户实体业务难支持、热点账户 |
| **存款** | 活期/定期、计息结息、双余额与日切 | 7×24 不间断与日终批处理的冲突、热点账户 |
| **贷款** | 授信、放款、还款计划、计息 | 产品与核算耦合、利率市场化 |
| **支付清算** | 转账、大小额、跨行清算、代收代付 | 清算账户热点、交易核算耦合 |
| **产品与定价** | 产品工厂、参数化配置、差异化定价 | 产品创新周期长、定制代码多 |
| **会计核算 / 总账** | 分录、总账、报表、业会分离 | 交易与核算强耦合、核算规则变更要停机 |
| **参数与运营** | 利率/费率/汇率配置、参数中心 | 参数散落、变更风险高 |
| **批量与日切** | 日终批处理、结息、跑批、日切 | 批处理窗口长、联机与批量互斥 |

> **共性判断**：这些痛点高度同源——**耦合**。交易与核算耦合、账户与产品耦合、业务与技术耦合。新一代核心的设计主线就是逐层解耦，再叠加分布式与信创。

## 一、热点账户：最高频的账务性能难题

### 业务场景与痛点

**热点账户**是被高频操作的账户：大量并发的余额增加、减少、冻结、解冻。它数量不多但操作频率极高，典型如代收付平台账户、商户收款账户、清算账户、双十一的支付宝中间账户、春节红包账户。

根因是账务处理的强事务性：每笔记账要先对账户资源加锁，完成后释放。同一时刻只有一个线程能持有锁，其余线程排队等待。并发越高，锁竞争越激烈，最终导致交易超时甚至雪崩。相关性能问题分三类：

- **死锁**：A→B 与 B→A 两笔转账并发，互相等待对方释放锁；
- **热点字段**：序号、流水号、余额、发生额等高频更新字段；
- **热点事件**：双十一、发红包等瞬时高并发场景引爆热点字段。

### 解决方案（六种主流做法及取舍）

| 方案 | 做法 | 适用 | 局限 |
|---|---|---|---|
| **汇总明细入账** | 联机只记流水（标志位"未入账"），定时汇总金额一笔入账 | 收单类入账 | 余额非实时；不适用于扣款类 |
| **控制并发数** | 对热点账户操作限流，约束同时请求的线程数 | 兜底手段 | 失败率上升，大行较少采用 |
| **缓冲入账（削峰填谷）** | 超过阈值(async)转可靠队列，低峰消化 | 短时脉冲流量 | 需维护队列；无"谷"可填时积压 |
| **子账户拆分（分桶）** | 一个账户拆成多个隐藏影子账户，hash 分散记账 | 长期高并发大商户 | 单桶余额可能不足，余额查询变复杂，金额均分难 |
| **内存数据库 + 缓存入账** | Redis 前置扣减，定时刷流水回库 | 超高并发 | 缓存与库一致性、并发冲扣易错账 |
| **硬件升级** | 提升 CPU/内存/IO | 备选 | 无法根治单点并发压力 |

**业界主流的组合打法**：

- 短时超高并发（红包、大促）→ **缓存扣款 + 异步批量**组合；长期热点（大商户）→ **账户拆分**。
- 平安银行新一代核心采用 **"联机无锁 + 异步汇总"**：联机并发交易不直接更新余额，仅插入增量明细，通过"不可见→可见→可用"三态流转实现并发可见性与隔离，配合增量校验与补偿防透支；异步汇总引入基于 Token 的分片调度实现任务分层并发。以"重应用、轻数据库"把核心逻辑下沉到应用层，借方热点单账户 TPS 超 1200、贷方超 5000。

> **可借鉴的关键点**：热点账户没有银弹。**收单类（只增）和扣款类（要校验余额）解法不同**——前者可异步汇总，后者必须解决"余额是否足够"的实时判定。任何方案都要回答两个底线问题：**余额不准多扣少扣、流水期末期初金额不能错**。缓存方案尤其要防"扣成负数"与冲扣并发导致金额混乱。

来源：[银行核心系统之热点账户（twt）](https://www.talkwithtrend.com/Article/243849)、[平安银行新一代分布式核心（热点账户攻坚）](https://m.toutiao.com/article/7626952021127741992)、[Java 生态下的核心银行系统实现](http://ynotes.cc/JAVA%E7%94%9F%E6%80%81%E7%9A%84%E7%8E%B0%E4%BB%A3%E9%93%B6%E8%A1%8C%E6%A0%B8%E5%BF%83)。

## 二、交易与核算耦合：业会分离

### 业务场景与痛点

传统核心既处理前台业务、又处理后台账务：一笔交易同时驱动账户变动、分录、总账。耦合带来三个问题：核算规则变更要改核心代码并停机投产；账户、科目、核算强绑定，业务灵活性差；核心系统臃肿、响应慢。

### 解决方案

**业会分离（交易核算分离）**：核心专注交易处理与产品管理，会计核算剥离到独立的**会计引擎 / 核算中台**，总账系统统筹报表。交易产生业务流水，会计引擎按参数化规则生成分录并送总账。

多地实践验证了这条路径的收益：

- **昆山农商银行**上线会计引擎后，查询类交易平均响应降至 100 毫秒内，季度结息约 17 分钟，日终批量从 3 小时缩短到约 10 分钟；核算要素参数化覆盖 5000+ 业务场景，新产品参数配置周期由两周缩短到 1—2 天。
- **广西农商联合银行**遵循"业会分离"解除账户、科目、核算强耦合，计息、计提调整无需核心停机；业务服务层按公共运营、对私存款、对公存款、贷款中心、内部账中心、IC 卡中心划成 6 个独立微服务，各服务独享数据库。
- **神州信息**在省级农商行新核心中把"交易与核算分离"列为核心能力，通过全行会计核算引擎实现交易核算完全分离并保证全行账务一致。

> **可借鉴的关键点**：业会分离的收益不只是"解耦"——它把**核算规则变更**从"核心停机投产事件"变成"参数配置事件"，这是业务敏捷性的关键。配套必须有**全行统一核算体系**，否则从"核心内耦合"变成"多系统核算 Data 不一致"（某省农信原痛点正是各交易系统各自独立核算、数据凌乱）。

来源：[昆山农商银行会计引擎](https://dzb.xfrb.com.cn/Html/2021-11-25/43021.html)、[广西农商联合银行核心实践](https://www.fintechinchina.com/cases/9870)、[神州信息省级农商行新核心](https://www.financeun.com/newsDetail/63327.shtml)。

## 三、7×24 不间断 vs 日终批处理：双余额与毫秒级日切

### 业务场景与痛点

银行账务天然有"日切"概念——交易要归属到某个会计日期。传统模式是"日终停机跑批"：日间联机、日终批量串行，批处理窗口长达数小时，期间无法 7×24 服务。互联网业务要求全天不间断，联机与批量必须并行。

### 解决方案

- **双余额 + 双日期设计**：账户同时维护两个会计日期的余额，日切瞬间联机与批量并行处理，确保交易不丢单、不重复记账。广西农商联合银行用这套"毫秒级日切方案"支撑 7×24 不间断服务。
- **双余额模式 + 交易核算分离**：赣州银行以此实现 24 小时营业；同时建立独立会计引擎与业务总账，实现准实时价税分离。
- **联机与批量微服务分离**：广东华兴银行新核心每个服务模块内部再分联机和批量独立微服务，架构分层、松耦合、可横向扩展。
- **批处理优化**：新疆农信通过优化批处理结构、合理规划调度流程缩短跑批时间；引入 DBIO 模块做两级数据缓冲，把单交易应用与数据库的平均通讯次数从 250 次降到 100 次，显著减轻后台库压力。

> **可借鉴的关键点**：解决"联机 vs 批量"冲突有两层手段——**架构层**做联机/批量分离、双余额日切（治本）；**性能层**做调度优化、减少库访问次数（治标）。单靠优化跑批速度无法真正实现 7×24，必须从账务模型上支持双日期。

来源：[广西农商联合银行核心实践](https://www.fintechinchina.com/cases/9870)、[赣州银行全云化国产转型](https://www.toutiao.com/article/7594819492165730868/)、[广东华兴银行分布式新核心](https://www.fintechinchina.com/solutions/5956)、[新疆农信产品工厂核心](https://www.fintechinchina.com/solutions/855)。

## 四、产品创新慢：产品工厂与参数化

### 业务场景与痛点

传统核心的产品靠硬编码定制，新产品上线要改代码、走完整投产流程，周期长。利率市场化后，差异化定价、快速产品创新成为竞争焦点。

### 解决方案

- **企业级产品工厂**：产品组件化、可复用部件组装，全生命周期管理（创意→需求→开立→销售→统计→下线），支持试算与灰度发布。赣州银行、神州信息均采用；新疆农信通过组件化快速推出存贷款组合产品。
- **定价工厂 + 规则引擎**：通过利率、费率、汇率、税率等定价因子和模型实现差异化计价，新增因子即可扩展。新疆农信支持固定/浮动/特殊利率、按金额与期限的分段计息；神州信息用丰富定价因子实现个性化服务。
- **参数化运营**：利率、费率集中配置，新产品主要靠参数落地。广西农商联合银行新产品以配置为主，减少定制代码。

> **可借鉴的关键点**：产品工厂的价值在**把"改代码"变成"配参数"**。判据是——新产品能否主要通过组装已有部件 + 配置参数完成，而无需修改核心代码。参数化必须配套**参数管控**（申请、验证、审计），否则参数配置本身成为新的风险源（平安贷记卡核心的做法是参数集中管理 + 条线化分类 + 分级分权）。

来源：[新疆农信产品工厂核心](https://www.fintechinchina.com/solutions/855)、[神州信息省级农商行新核心](https://www.financeun.com/newsDetail/63327.shtml)、[赣州银行全云化国产转型](https://www.toutiao.com/article/7594819492165730868/)。

## 五、客户与账户体系：统一视图与多层级账户

### 业务场景与痛点

- **客户数据割裂**：账户离散分布在不同应用系统，无法形成统一客户视图；II/III 类账户升降级等跨账户实体业务难支持；账户相关系统耦合过高、存在循环依赖，交易链路冗长。
- **多法人合并**：省级银行合并重组后，多机构系统异构、数据标准不一、账户体系分散，多法人并行托管、渐进式合并难度极高。

### 解决方案

- **客户中心化**：构建统一客户信息模块，沉淀主数据、统一客户视图，支持多法人客户管理。
- **灵活账户结构**：支持母虚子实、母实子虚、母实子实等多层级账户管理，满足线上线下多类账户需求（神州信息）；以客户为中心构建账户核心，支持 II/III 类账户（中电金信）。
- **服务解耦**：广东华兴银行把原分散的核心、贷款、储蓄、电子账户、综合账户体系汇聚，构建含产品定价、公共运营、参数、存款、贷款等功能模块的全功能核心，各模块联机/批量分离、松耦合。
- **多法人托管**：存款、贷款、客户、合约、总账全面解耦，支持多法人托管与渐进式合并（神州信息）。

> **可借鉴的关键点**：账户体系重构往往是合并重组类银行的**第一优先级**——因为账户是客户、产品、核算的共同锚点。账户模型不统一，客户视图、产品体系、核算系统都无法统一。

来源：[广东华兴银行分布式新核心](https://www.fintechinchina.com/solutions/5956)、[神州信息省级城商行新核心](https://www.financeun.com/newsDetail/64105.shtml)、[中电金信某省农信新核心](https://www.gientech.com/detail/70.html)。

## 六、清算热点与分布式事务

### 业务场景与痛点

清算账户是典型的热点账户（代收付、服务费、平台层账户瞬时高并发）。同时，跨服务、跨分片的资金流转需要保证一致性，不能依赖数据库层回滚外部不可逆资源。

### 解决方案

- **清算热点**：纳入热点账户统一治理（见第一节），按收单类/扣款类选择异步汇总或余额实时校验方案。
- **多元化分布式事务**：平安银行自研分布式事务引擎基于两阶段提交，一阶段资源预留、二阶段提交或释放；基于事件溯源把事务事件持久化到各参与方，支持幂等与防悬挂、去中心化管理；支持 TCC 与 Saga 混合编排，按场景选择。
- **异步/实时清算**：核心支持业务流水、分录流水、异步/实时清算，按全行核算体系设计（中电金信）。

> **可借鉴的关键点**：分布式事务引擎要**按场景选模式**而非一刀切——资金类用 TCC/Saga 在业务层冻结补偿，内部可控 CRUD 可用 AT 模式。事件溯源 + 事务上下文传递是保障幂等、防悬挂的关键工程手段（模式原理见 [architecture.md](architecture.md)、[migration.md](migration.md)）。

来源：[平安银行新一代分布式核心](https://m.toutiao.com/article/7626952021127741992)、[中电金信某省农信新核心](https://www.gientech.com/detail/70.html)。

## 七、数据标准与全链路追溯

### 业务场景与痛点

老核心交易链路难追溯、数据标准不统一、跨系统信息难对齐，影响监管合规、风险管理、反诈与报送。

### 解决方案

- **全局流水号**：核心流水深度嵌入分类、场景、行为元素，用全局流水号串联交易全生命周期，实现跨系统、跨模块全流程追溯（广西农商联合银行）。
- **数据落标到字段级**：统一全行数据口径与标准，支撑监管合规、反诈与报送（广西农商联合银行）。
- **数据治理贯穿建设**：从管理制度、业务流程、技术功能各层面校订数据标准、完善数据要素，为精细化管理与数据资产化打基础（神州信息）。

> **可借鉴的关键点**：数据标准要在新核心建设期就"贯标"，而不是上线后补。流水号设计要前置考虑追溯维度（分类/场景/行为），否则事后无法还原交易链路。

来源：[广西农商联合银行核心实践](https://www.fintechinchina.com/cases/9870)、[神州信息省级农商行新核心](https://www.financeun.com/newsDetail/63327.shtml)。

## 痛点—方案速查表

| 痛点 | 首选方案 | 关键判据 |
|---|---|---|
| 热点账户（入账类） | 汇总明细入账 / 异步批量 | 接受余额非实时；流水金额必须准 |
| 热点账户（扣款类） | 缓存扣款 / 子账户拆分 | 必须实时校验余额、防透支与并发错账 |
| 交易核算耦合 | 业会分离 + 会计引擎 | 需配套全行统一核算体系 |
| 日终停机跑批 | 双余额 + 双日期日切 + 联机批量分离 | 从账务模型支持，非单纯优化跑批 |
| 产品创新慢 | 产品工厂 + 参数化 + 定价工厂 | 新产品能否不改代码、只配参数 |
| 客户/账户割裂 | 客户中心 + 多层级账户模型 | 账户是客户/产品/核算的共同锚点 |
| 分布式事务一致性 | TCC/Saga + 事件溯源 | 资金类业务层冻结补偿，按场景选模式 |
| 数据难追溯 | 全局流水号 + 字段级落标 | 建设期贯标，前置设计追溯维度 |
