# 迁移方法论

核心系统改造最难的不是新技术，而是**迁移切换**——核心系统一天都不能停。

## 改造路径选择

| 路径 | 说明 | 适用 |
|---|---|---|
| 直接重构 | 全新架构重写核心 | 中小银行、新建银行 |
| 渐进式下移 | 按业务模块逐步迁移 | 大型银行 |
| 双核并行 | 新老核心同时运行一段时间 | 过渡期风控要求高的银行 |
| 外围先行 | 先改造渠道、外围系统，核心最后动 | 风险最敏感的银行 |

## 改造序列：被验证的渐进路径（2026-11 补充）

大行实践收敛出一条**风险递增的迁移序列**——「从外围到核心、从小到大额、从低并发到高并发」：

| 阶段 | 业务类型 | 中信 GoldenDB 实证 |
|---|---|---|
| 1 外围查询 | 无资金交易 | 2015-09 冠字号查询 |
| 2 小额资金 | 小额、可承受 | 2016-05 门户网站 |
| 3 大额交易型 | 金额大但量小 | 2016-11 金融同业平台 |
| 4 高并发明细 | 交易量大、含隐性资金 | 2017-06 零售统一积分 |
| 5 信用卡核心 | 亿级账户、独立闭环 | 2019-10 StarCard |
| 6 账务核心 | 全行总账中枢 | 2020-05 凌云 |

> 中信从立项到账务核心投产走了 **6 年**（2014→2020），核心迁移预研始于 2017、正式启动「凌云工程」于 2018-03。这个节奏被广发、浦发等后续银行不同程度复制。**结论：核心切换的速度上限由验证充分度决定，不是由技术能力决定。** 来源：[中兴官网](https://zte.com.cn/china/enterpriseindustry/financial_sector/chenggonggushi/202111161622.html)（一手）。

## 双轨并行 + 灰度切流（标准打法）

1. **双轨运行**：新老核心同时记账，交易双发或镜像回放
2. **数据核对**：逐笔比对两套系统的账务结果（余额、流水、总账）
3. **灰度切流**：按客户 / 业务 / 网点维度逐步把流量切到新核心
   - 内部员工 → 少量白名单客户 → 某区域 / 某业务线 → 全量
4. **回退预案**：每个灰度阶段必须有可快速回退的开关
5. **全量切换**：核对通过后全量切换，老核心转为只读，观察期后下线

## 关键工程问题

- **数据迁移**：历史数据（几十年账务）搬迁与格式转换；新旧科目映射
- **停机窗口**：能否做到秒级 / 分钟级切换（依赖数据同步链路 RPO≈0）
- **性能对齐**：新核心吞吐需满足峰值（可用全链路压测验证）
- **批处理对齐**：日终批量结果与老核心逐科目核对
- **外围系统适配**：数百个外围系统的接口改造与回归测试

## 风险清单

- 老核心逻辑"黑盒"：缺乏文档，隐性规则在迁移中丢失 → 需要交易回放比对
- 切流后长尾问题：低频业务（销户、挂失、司法冻结）未覆盖测试
- 双轨期间成本翻倍，核对平台本身成为新系统

## 工程方法体系（2026-11 新增）

> 单靠功能测试不足以覆盖分布式核心切换风险。以下是从大行实践中沉淀的一套完整方法体系，四个环节缺一不可。

| 环节 | 方法 | 参考 |
|---|---|---|
| **交易回放比对** | 生产日志脱敏回放；网络流量录制 + 旁路 TAP 镜像；**交易级 + 数据库级两层级比对** | 农行研发中心《分布式核心银行系统的测试研究与实践》（《金融电子化》2020-05）；神州信息 Sm@rtComplay；华青融天 EZSonar（见 [resources.md](../resources.md)） |
| **数据一致性核对** | 余额恒等式、通道账单标准化、差异中心与自动修复；Flink SQL 分钟级差异检测 | [Wallet Reconciliation（2026-08）](../resources.md) |
| **混沌演练** | 网络延迟/服务宕机/CPU 抢占故障注入，设定爆炸半径与自动中止 | ChaosBlade；中电金信银行核心测试方案 |
| **全链路压测** | JMeter 单交易基准/负载/混合/稳定场景；类网关统一发压；80% 交易量在 20% 时间内完成推算 TPS | 农行分布式核心性能测试实践 |

### 工行「六步实施工艺」（2025 年完成全行主机下移）

1. 下主机应用平台服务入口建设
2. 配合应用改造
3. 配合应用切流
4. 下主机应用平台功能建设
5. 下主机应用主机平台并行
6. 以平台为准提供服务

策略是「**解耦先行、分步迁移、安全兜底**」：前三步完成转型路径解耦，后三步按「先境内后境外、先个人再对公」迁移。配套安全机制：仿真环境注入生产流量、关键场景 100% 仿真核对；多批次多维度灰度切流；单交易/单批次/全流量的**三级应急回切**，生产故障 2 分钟内恢复。来源：[陈志祥署名长文，《中国金融电脑》2026 年第 6 期](https://finance.sina.com.cn/wm/2026-06-25/doc-inierihw2510401.shtml)（一手）

### 其他迁移工艺参照

- **四川农商联合银行**：企业架构 + 业务建模驱动微服务；新旧系统并行动态迁移，客户无感；2025-11-15 投产、2025-12-24 大机下电（[中电金信](https://www.gientech.com/detail/1672.html)）
- **农发行「涅槃」工程**：双轨并行 + 七步投产 + 哨兵守护；两地三中心 12 副本，RPO=0、RTO≤20 秒
- **中信银行**：RPG2JAVA 代码翻译与仿真比对工具，新老系统 24 个月同步研发发版（见 [cases.md](../cases.md)）

### 厂商协同模式：天使客户与联合研发（2026-11 补充）

国产数据库进入银行核心，靠的不是招标 benchmark，而是**长期联合研发 + 稳定运行换信任**：

| 案例 | 联合研发周期 | 上线标准 |
|---|---|---|
| GoldenDB × 中信银行 | 2014 立项 → 2020 账务核心，6 年 | 外围业务先跑 5 年，核心切换前数十轮跟账验证 + 试运行 + 切换演练 |
| OceanBase × 网商 / 蚂蚁 | 2010 立项 → 2015 银行核心，5 年 | 先在支付宝双十一承担部分 → 100% 交易流量，再进网商银行全核心 |
| GaussDB × 工行 / 招行 | 2014 进工行 EDW → 2018 招行 OLTP，4 年 | OLAP 先验证，再 OLTP，再 HTAP |

> **「TPC-C 是入场券，稳定运行年限才是录取通知书」**——选型时应要求候选库提供同类核心场景的**连续运行年限与零事故记录**，而非仅看 benchmark 排名（见 [databases.md](../databases.md)）。

### 上线判据：什么时候才算迁移完成（2026-11 补充）

| 判据 | 说明 |
|---|---|
| 双轨账务逐笔一致 | 交易级 + 数据库级两层级比对，差异清零 |
| 全量业务覆盖 | 含低频长尾（销户 / 挂失 / 司法冻结）——最易在切流后爆雷 |
| 切换演练轮次充分 | 中信账务核心切换前做了 **十轮**演练 |
| 回切开关有效 | 单交易 / 单批次 / 全流量三级回切，生产故障分钟级恢复 |
| 观察期后老核心只读下线 | 双核并行不是终点，**单轨运行**才是（中行核心正朝「单轨运行」推进） |
