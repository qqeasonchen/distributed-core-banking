# 架构方案

## 总体分层

```
渠道层（手机银行 / 网银 / 柜面 / 开放 API）
        ↓
集成层（企业服务总线 / API 网关 / 服务网格）
        ↓
核心层（微服务：账户、存款、贷款、支付、清算、总账）
        ↓
数据层（分布式数据库 + 缓存 + 消息队列）
        ↓
基础设施（x86 集群 / 容器平台 K8s / 多数据中心）
```

## 微服务拆分

单体核心通常按业务域拆分为：

- 客户信息管理（CIF）
- 存款服务（活期 / 定期）
- 贷款服务（放款 / 还款 / 计息）
- 支付与清算服务
- 总账服务
- 公共服务（日终批量、参数管理、额度）

常用技术栈：Spring Cloud / Dubbo、Kubernetes、服务注册发现（Nacos / ZooKeeper）、分布式事务框架（Seata 等）。

## 企业级业务建模：架构改造的前置工序（2026-11 补充）

大行分布式核心的共同前置动作是**企业级业务建模**——先把全行业务抽象为标准化组件，再做技术拆分。这是「业务架构驱动技术架构」，而非对旧系统做技术平移。

| 银行 | 建模规模 / 方法 | 产出 |
|---|---|---|
| 工商银行 | 63 个业务领域 / 5200+ 任务组件 | 六步实施工艺 + 40+ 标准化设计方案 |
| 邮储银行 | 企业级业务建模 + IT 实施工艺 | 「解耦—重构—复用」积木式产品组合；大型银行中率先同时采用建模 + 微服务 |
| 四川农商联合银行 | 企业架构 + 业务建模驱动微服务 | 新旧系统并行动态迁移、客户无感 |

> **工程价值**：建模统一了业务语言与组件边界，使「单体 → 微服务」的拆分有据可依，避免把旧系统的烟囱接口原样搬进分布式架构。来源见 [cases.md](../cases.md) 各银行专章。

## 改造序列：先外围后核心、先信用卡后账务（2026-11 补充）

分布式核心改造存在一条被反复验证的**通用序列**：

```
外围查询类（冠字号/积分）
  → 渠道与小额交易（门户/电子渠道）
    → 信用卡核心（相对独立、账务闭环）
      → 账务核心 / 总账（全行中枢，最后动）
```

| 银行 | 信用卡核心 | 账务 / 银行核心 | 说明 |
|---|---|---|---|
| 中信银行 | 2019-10（StarCard） | 2020-05（凌云账务核心） | 信用卡先行，间隔 7 个月 |
| 浦发银行 | 2024-09（信用卡核心） | 2025-05（零售分布式核心） | 信用卡先行，间隔 8 个月 |
| 广发银行 | 2024（信用卡核心） | 2023（分布式银行核心） | 银行核心先行，路径因行而异 |

> **结论**：「先外围、后核心」是共识，但核心内部先信用卡还是先账务因行而异——取决于哪块业务更独立、更易灰度验证。共性是把风险最高的全行总账放在有充分双轨验证之后再动。来源：[cases.md](../cases.md)、[databases.md](../databases.md)。

## 事务一致性

核心账务要求强一致，分布式架构下常用方案：

| 方案 | 说明 | 适用 |
|---|---|---|
| Raft / Paxos 多数派 | 分布式数据库内部副本一致性 | 数据库层 |
| TCC（Try-Confirm-Cancel） | 业务层两阶段补偿 | 跨服务转账 |
| Saga | 长事务拆分为本地事务序列 + 补偿 | 跨域流程 |
| 最终一致 + 对账 | 异步消息 + 日终核对 | 非关键路径 |

> **金融场景分界线**（2026-11 补充）：Seata 四模式中，**AT 仅限可控的内部 CRUD**（undo log 无法覆盖外部不可逆资源）；**资金类业务必须走 TCC 或 SAGA，在业务层做「冻结 + 补偿」**。核心判断是「资金回滚是业务设计问题，不是数据库回滚问题」。参见 [resources.md](../resources.md) 分布式事务专题。

## 分布式数据库

见 [databases.md](../databases.md)。共性能力：

- 计算存储分离，水平扩展
- Multi-Raft / Paxos 多副本强一致
- 分布式事务（全局时钟 / TSO 或 Hybrid Logical Clock）
- 兼容 MySQL / Oracle 语法，降低迁移成本

## 高可用与多活

| 方案 | RPO / RTO | 说明 |
|---|---|---|
| 同城双活 | RPO≈0 | 两机房同时承载流量，延迟敏感 |
| 两地三中心 | RPO≈0 / 分钟级 | 同城双活 + 异地灾备 |
| 异地多活 | RPO≈0（单元化） | 按用户分片（单元化 / Set 化），多地同时提供服务 |

单元化（Set 化）是蚂蚁 LDC（Logic Data Center）架构的核心思想：将数据和流量按维度切分到独立单元，单元内闭环，故障时整体切换。

## 单元化：小单元化 vs 大单元化

> 来源：公众号"financial基础架构"《为什么银行业有两种单元化架构？——从集中式分库到分布式多活的演进》（2026-05）：[原文链接](https://mp.weixin.qq.com/s/MGbAVoTVU4PvrIKMievtOw)

银行业存在两种典型单元化架构：

| 维度 | 小单元化 | 大单元化 |
|---|---|---|
| 数据库底座 | 集中式数据库 | 分布式数据库 |
| 拆分方式 | 用户编号范围（连续区间，如 1~5000 → DB1） | 客户 ID 后两位 Hash（均匀散列 00~99 共 100 份） |
| 扩展性 | 新增单元解决新增用户，单元内热点无法动态调整 | Hash 均衡 + 弹性扩缩容，单元间流量可动态调拨 |
| 容灾等级 | 同城级别 | 数据中心级 / 城市级多活 |
| 容灾方式 | 依赖运维切换 | "约定大于配置"，单笔业务自动容灾 |
| 资源利用率 | 峰值 60% 即需扩容，日常水位偏低 | Leader 混合部署均衡读写，利用率大幅提升 |
| 跨单元事务 | 本地事务为主，跨库特殊处理 | 统一视为分布式事务，架构一致性强 |
| 适用阶段 | 业务初期、容灾要求不高 | 业务成熟期、需数据中心级容灾 |

### 大单元化三层架构要点

- **接入层**：VIP 负载均衡 + 流量识别，持有全局用户映射表；无线端启用"服务 IP 优先级"后通常无需转发
- **业务应用层**：识别跨单元业务（约 5%），跨单元（如转账）统一走分布式事务中间件；应用连接所有数据库副本是实现无状态与快速容灾的基础
- **数据访问层**：流量调拨期间应用流量与 Leader 可能短暂不一致，要求数据库具备备节点到主节点的自动转发能力

### 成本结论

**机器资源成本仅与容灾能力正相关，与单元化无关**。单元化不增加 CPU/内存占用、节约磁盘空间，且"业务链路机房内闭环"使链路 RT 下降、TPS 提升。两种架构是演进关系而非替代关系：小单元化是"分"的起点，大单元化是"分而能活"的终态。

## 日终批处理改造

集中式核心依赖大型机批处理窗口；分布式化后需要：

- 批处理任务调度拆分与并行化（如按账户分片）
- 批量与联动的资源隔离
- 核对平台：账证核对、总分核对自动化

### 现代答案：流批一体 + 事件驱动持续对账（新增）

2025—2026 的实践表明，方向不是「更快地跑批」，而是**把 T+1 批量对账改造成事件驱动的持续对账**：

| 案例 | 做法 | 效果 |
|---|---|---|
| AWS × Zeta | Flink（流批统一）+ Kafka + EKS + S3，可扩展至 23000+ Spot 实例 | 2.08 亿信用账户 **40 分钟**完成 EOD |
| VBill Payment × StarRocks | Flink CDC + StarRocks 主键表替代 Hive/HBase/Kudu | 批处理扫描量 **-73%**，报表生成缩短 3+ 小时 |
| 光大银行信用卡中心 | S/T/A/D 四层实时数仓，Flink + Paimon 湖仓一体，日终对账补偿机制 | 《中国信用卡》2024 年第 11 期 |

事件驱动对账通用范式：Flink interval join + 会话窗口 + exactly-once + 未匹配事件异常队列。详见 [resources.md](../resources.md)。

## 核心系统上云与多活新形态（新增）

- **一云多芯**：工行率先落地，统一云平台管理多种 CPU 架构服务器，化解供应链风险；浦发、四川农商亦采用
- **两地四中心 / 四地八中心**：工行「两地四中心」双主模式（同城双活 + 异地双站点灾备），演练验证 2 分钟内园区级接管且零数据丢失；腾讯 TCE 支撑某国有大行「四地八中心多活」（8 万+ 节点专有云，二手来源）
- **多地多活单元化**：四川农商联合银行在成都/雅安/泸州三地部署四个物理数据中心，客户数据拆分 + 流量灵活调度 + 故障精细隔离（[中电金信案例](../cases.md)）
- **开源参照**：阿里 [AppActive](https://github.com/alibaba/Appactive) 提供多活标准 + 实现 + Demo（注意核心代码停留在 2021—2022，低活跃维护）

## 全栈信创架构栈（2026-11 补充）

国内大行的分布式核心普遍采用「一云多芯 + 国产数据库 + 国产 OS」的全栈替代：

| 层 | 典型选型 | 案例 |
|---|---|---|
| 芯片 | 鲲鹏 / 海光 C86 / 飞腾 | 建行（鲲鹏）、国开行（海光 C86） |
| 操作系统 | 麒麟 / 统信 | 建行、国开行（麒麟） |
| 数据库 | GaussDB / GoldenDB / TDSQL / OceanBase | 见 [databases.md](../databases.md) |
| 云平台 | 一云多芯统一云管 | 工行、浦发、四川农商 |
| 中间件 | 国产消息 / 交易中间件 | 阿里 / 腾讯 / 华为生态 |

> 「一云多芯」（统一云平台纳管多种 CPU 架构）是工行率先落地的供应链风险化解手段，后被多家大行采用。来源：[cases.md](../cases.md) 工行 / 建行 / 国开行专章。

## 核心与渠道解耦：core-agnostic（2026-11 补充）

国际主线与国内「信创驱动」不同，强调**核心与渠道解耦**：

- 渠道层（手机银行 / 网银 / 开放 API）与核心层通过标准 API 隔离，核心可替换而不影响渠道
- Thought Machine 三层架构（云基础设施 / 核心能力 / 产品逻辑）把产品配置与核心引擎完全分离，产品团队改产品无需等厂商发版
- 开放银行（PSD2 / UK Open Banking）强制核心 API 化，反向推动了解耦
- **判断**：这与国内「稳态 / 敏态双态」是同一诉求的两种表达——**让创新层快速迭代，让核心层稳如磐石**。来源：[vendors.md](../vendors.md)、[papers.md](../papers.md) 国际监管章
