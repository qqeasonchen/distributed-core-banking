# 核心概念

## Core Banking（核心银行系统）

银行用来支撑最基础业务运转的后台核心系统，是银行的"总账本 + 发动机"。

### 功能范围

- **客户与账户管理**：开立储蓄卡、信用卡、存款账户，维护客户信息
- **存款业务**：活期、定期、利息计算与结息
- **贷款业务**：放款、还款计划、利息计提
- **支付结算**：转账、跨行清算、代收代付
- **总账与会计**：所有交易入账，产出日终账务、对账单

### 关键特征

| 特征 | 说明 |
|---|---|
| 集中性 | 全行统一的一套系统，而非每个网点各一套 |
| 7×24 运行 | 支持日终批处理（batch）与实时交易 |
| 强一致性 | 余额、账务必须绝对准确 |
| 高稳定性 | 宕机即全行业务停摆 |

### 概念辨析

- Core Banking ≠ 手机银行、网银（后者是"渠道层"前台）
- Core Banking ≠ 信贷系统、反洗钱系统（外围专业系统，通过接口对接）
- **"分布式核心"不是所有层都分布式**（2026-11 补充）：账务的强一致单元内部仍是"集中式"逻辑，分布式体现在应用微服务化、数据分片多副本、基础设施池化三层

### "分布式"到底分布在哪些层（2026-11 补充）

| 层 | 分布式体现 | 保持不变的部分 |
|---|---|---|
| 应用层 | 单体 → 微服务，按业务域拆分，无状态化 | 交易逻辑与会计规则不变 |
| 数据层 | 分库分表 / 原生分布式数据库，多副本 | 单笔账务的 ACID 强一致不可妥协 |
| 事务层 | 跨服务用 TCC / SAGA，库内用 2PC / 共识 | 资金类必须业务层冻结 + 补偿 |
| 基础设施 | x86 + 容器 + 多数据中心 | 高可用与容灾目标不变 |

> **结论**：分布式核心解决的是**扩展性、成本、自主可控**，不解决也不削弱**账务强一致**——后者靠数据库共识协议 + 业务层事务设计共同保证。

### 稳态与敏态：双态 / 三态架构（2026-11 补充）

| 形态 | 特征 | 落地形态 |
|---|---|---|
| 稳态（Steady） | 核心账务，强一致、高可用、变更审慎 | 传统核心、存款 / 贷款账务 |
| 敏态（Agile） | 渠道 / 产品创新，快速迭代 | 互联网贷款、开放银行产品 |
| 智态（Intelligent） | 数据智能与 AI 能力 | 农发行「涅槃」工程「稳态 + 敏态 + 智态」三态合一 |

- 平安银行新一代核心采用「敏稳双态」设计（2025，媒体报道口径，见 [cases.md](../cases.md)）
- 双态的本质是**不同业务对一致性 / 迭代速度的要求不同**，用架构隔离而非一刀切；与国际 core-agnostic 是同一诉求的两种表达（见 [architecture.md](architecture.md)）

## 集中式 vs 分布式架构

| 维度 | 传统集中式核心 | 分布式核心 |
|---|---|---|
| 硬件 | IBM 大型机 / 小型机 | x86 普通服务器集群 |
| 数据库 | Oracle、DB2 | 分布式数据库 |
| 应用架构 | 单体应用 | 微服务（Dubbo / Spring Cloud） |
| 扩展方式 | Scale-up（换更大机器） | Scale-out（水平加节点） |
| 可用性 | 单点，依赖主机高可靠 | 多副本，单点故障可自动接管 |
| 成本 | 软硬件昂贵，受制于供应商 | 普通硬件，自主可控 |

## 分布式化的驱动力

1. **扩展瓶颈**：移动银行与支付峰值（如双十一）流量增长，集中式只能垂直扩容，成本指数上升
2. **单点风险**：主机故障即全行停摆
3. **信创 / 去 IOE**：国产化替代政策，摆脱对 IBM / Oracle / EMC 的依赖

### 两条驱动主线：国内 vs 国际（2026-11 补充）

| 维度 | 国内主线 | 国际主线 |
|---|---|---|
| 驱动力 | 信创 / 安全可控 / 自主可控 | 降本（mainframe debt）+ 产品敏捷 |
| 技术路径 | 分布式数据库 + 微服务 + 单元化 | 云原生核心 + SaaS + core-agnostic |
| 代表 | 工行 / 邮储去主机、GoldenDB / OceanBase | Thought Machine Vault、Temenos SaaS |
| 迁移模式 | 双轨并行 + 灰度切流，长周期（3—6 年） | 核心与渠道解耦，分产品线迁移 |

> 两条路径殊途同归：**核心与渠道解耦、账务强一致不可妥协、迁移风险是第一约束**。来源：[cases.md](../cases.md) 国际案例章、[vendors.md](../vendors.md) 趋势判断。

### 政策起点：2014 年银监会 39 号文

> 完整发展脉络见 [timeline.md](../timeline.md)；政策原文与文号见 [papers.md](../papers.md)。

- **2014**：银监会等四部委《关于应用安全可控信息技术、加强银行业网络安全和信息化建设的指导意见》（银监发〔2014〕39 号）发布，要求自 2015 年起安全可控技术应用比例逐年不低于 15%，2019 年总体达 75% 左右——这是银行业「去 IOE / 信创」的起点文件。
- **2016**：《中国银行业信息科技发展"十三五"规划》提出「十三五」末面向互联网场景的重要信息系统全部迁移至云架构，其他系统迁移比例不低于 60%。
- **2019 / 2022**：央行《金融科技发展规划》两轮（银发〔2019〕209 号 / 2022—2025 年），后者明确「稳妥推进信息系统向多节点并行运行、数据分布存储、动态负载均衡的分布式架构转型」。
- **2020 / 2021 / 2022**：金融信创一/二/三期试点，从 47 家头部机构扩至 198 家，再到计划覆盖全行业 5000+ 家金融机构。

> 去 IOE 概念源自阿里：2008 年王坚提出，2013-05 支付宝最后一台 IBM 小型机下线，2013 年 EMC 存储全部下线；棱镜门（2013）后上升为国家安全议题，金融业随之跟进。

## 常见误区辨析（2026-11 补充）

| 误区 | 实际情况 |
|---|---|
| 「上了分布式数据库 = 完成分布式核心改造」 | 数据库只是数据层；应用微服务化、事务改造、外围适配、迁移工程同样关键 |
| 「TPC-C 榜首 = 能上金融核心」 | 金融核心看的是稳定运行年限 + 零事故，benchmark 是入场券不是终点（见 [databases.md](../databases.md)） |
| 「单元化 = 越多越好」 | 单元化是容灾手段，机器成本与容灾能力正相关、与单元化本身无关（见 [architecture.md](architecture.md)） |
| 「分布式 = 不要强一致」 | 账务强一致不可妥协，靠共识协议 + 业务层事务保证 |
| 「信创 = 国产替代一切」 | 39 号文用的是「安全可控」而非「国产化」，强调风险可控与自主掌握，不是一刀切 |
